# ACF v1.0.0 — read-only release

Agent Credential Firewall lets AI agents perform authorized semantic actions, such as listing DNS records, without ever holding the credential behind them. An agent asks a local daemon, the Capability Authority narrows and signs a task capability bound to that device's certificate, and the gateway calls the API with a credential from its encrypted store. Only allowlisted response fields come back, and every decision lands in a tamper-evident audit log.

**This release is read-only.** Every action classified `mutate` is refused, even when a capability grants it. Writes arrive with the approval service (M2).

## What is in it

| Binary | Role |
| --- | --- |
| `acf-gateway` | Credential gateway. mTLS only, production profile, encrypted local secret store, hash-chained audit with external checkpoints |
| `acf-control-plane` | Capability Authority (`serve`), checkpoint collector, `verify-audit`, and key and admission tools |
| `acf-agent` | Agent-side daemon on a permissioned Unix socket, a CLI, and the read-only MCP adapter (`acf-agent mcp`) |
| `acf-setup` | Generates a complete production deployment (`init`) and re-signs edited configuration (`admit`) |
| `acf-store` | Administers the encrypted secret store; values come from standard input only |

Start with `docs/deployment.md`. For MCP clients such as Claude Code, see `docs/mcp.md`. For a first real run, `docs/staging.md` walks through Cloudflare DNS read-only.

## Security properties

- **Agents never hold a credential.** They never see a capability either: the daemon keeps it, and the agent holds only an opaque, process-bound handle.
- **Requests must pass every check.** Each request needs:
  - a TLS 1.3 client certificate enrolled for the device;
  - a capability signed by the authority and bound to that certificate;
  - matching gateway policy and resource constraints;
  - a fresh, never-seen request ID.
- **Agent scope is only a proposal.** The authority grants the intersection of the proposal, the device's entitlements, an administrator-signed job definition (or configured scheduler), and the registered actions.
- **Configuration is admitted per role.** The bundle, each connector profile, and the policy need separate signatures, and production refuses to start on anything unadmitted, insecure, or pointed at a test destination.
- **Audit is tamper-evident.** Truncation or replacement of the audit log is detectable against the collector's checkpoints. Requests fail closed when checkpoints stall.
- **Reviewed:** see the v1.0 security review (`docs/security/v1-review.md` in the repository; `docs/security-review.md` in the release archive). It is an internal review, not an independent assessment.

## Known limitations

- **Read-only.** There is no approval service and no human task confirmation yet.
- **The secret store provides integrity, not rollback resistance.** Configuration must acknowledge `rollback_resistance: none`. An older copy of the store can bring back an older credential.
- **Store keys come from a systemd credential or a protected file.** No TPM, KMS, or interactive unlock.
- **One gateway per environment.** No high availability or shared state.
- **Administration is file-based.** Revocation, device enrollment, entitlements, and job definitions are edited as files; there is no administrative API or UI. Authority configuration and registries are protected by file ownership, not signatures (review finding V1-04).
- **No certificate renewal command.** Certificates expire after 90 days by default; reissue them from the offline CA.
- **No discovery tools in MCP.** Tell the agent which jobs, actions, and resources it may use.
- **Platform.** Linux x86-64 with glibc 2.35 or newer.

## Compatibility

From v1.0 on, the `acf.*/v1` configuration schemas, the capability and checkpoint wire formats (ADR 0003, ADR 0005), and the daemon local API, including the MCP tool schemas (`acf/toolsVersion` `v1`), change only in backward-compatible ways.
